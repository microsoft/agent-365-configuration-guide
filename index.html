Copilot Studio 에이전트

Copilot Studio(New experience)에서 만든 에이전트를 안전하게 운영하기 위한 기본 보안 설정을 처음부터 끝까지 안내합니다. 에이전트 생성 → 승인·배포 → 인벤토리 → 차단 → 기본 접근제어 → 리스크 탐지 → 리스크 기반 접근제어 → 런타임 보호 → 트래픽 모니터링까지, 각 단계에서 어떤 포털에 들어가 무엇을 설정하는지 스크린샷과 함께 순서대로 짚어 드립니다.

1단계 · 환경·권한 준비

New Copilot Studio 우측 상단의 환경 선택기에서 실습에 사용할 Power Platform 환경을 먼저 고정합니다. Power Platform 환경은 앱·에이전트·데이터(Dataverse)를 담는 격리된 컨테이너로, 환경마다 접근 권한·보안·DLP 정책이 따로 적용됩니다. 여기서 선택한 환경이 7장(런타임 보호)·8장(트래픽 모니터링)의 환경 단위 설정 대상과 동일해야 하므로, 처음부터 실습 환경을 정해두는 것이 중요합니다. 해당 환경에 대한 제작자(Maker) 이상의 역할이 필요합니다.

⚠️ Notice — 본 Agent 365 관련 데모는 기본 환경(Default Environment)에서도 따라 하실 수는 있으나, 실 운영 환경에서는 반드시 테스트를 위한 별도의 환경을 구성하시어 진행하셔야 합니다. 환경 개념·생성 방법은 Power Platform 환경 개요(공식 문서)를 참고하세요.

2단계 · 빈 에이전트 생성

Agents 화면에서 New agent를 선택해 템플릿이 아닌 빈 에이전트로 시작합니다. 빈 에이전트로 시작해야 지침·지식·도구를 하나씩 통제하면서 붙일 수 있고, 이후 승인 심사에서 무엇이 왜 붙었는지 설명하기 쉽습니다. 이 가이드에서는 Agent365-Guide-Demo라는 이름을 사용합니다.

3단계 · 지침·오케스트레이션

① 에이전트 이름, ② 지침(Instructions), ③ 모델·행동 설정 순으로 입력합니다. New experience에서는 모델과 오케스트레이션 설정 위치가 기존 UI와 달라 Settings > AI & behavior에서 확인해야 하며, 기존의 '생성형 AI' 토글과는 구분됩니다. 지침은 1장의 관리자 승인 심사에서 업무 목적을 판단하는 근거가 되므로 구체적으로 작성합니다.

4단계 · 지식 추가

Build > Add knowledge에서 SharePoint·OneDrive·Dataverse 등 지식 원본을 연결합니다. 여기서 붙인 지식은 1장의 관리자 승인 화면과 2장의 인벤토리 데이터 & 도구 탭에 그대로 노출되므로, 민감한 사이트를 연결할 때는 사전 검토가 필요합니다.

5단계 · 도구 구성

Build > Add tool > Model Context Protocol (MCP) 카탈로그에서 필요한 도구를 연결합니다. MCP 도구는 런타임에 실제로 호출되는 지점이므로, 5장(리스크 탐지)·7장(런타임 보호)·8장(트래픽 모니터링)에서 탐지·보호·로깅의 실제 대상이 됩니다.

6단계 · 테스트

Preview(테스트) 패널에서 한국어 프롬프트로 실행해 지식 인용과 도구 호출이 정상인지 확인합니다. 단, 테스트 패널에서 발생한 활동은 2장에서 보는 활성 사용자·세션 통계에는 집계되지 않습니다. 실제 사용량 확인은 게시된 채널에서 실행한 결과로 판단해야 합니다.

7단계 · 게시·채널 연결

구성이 끝나면 게시 다이얼로그에서 채널 추가를 시작합니다. 게시는 '에이전트를 저장하는 것'이 아니라 사용자에게 노출될 경로를 여는 것이라는 점을 구분합니다.
채널 선택기에서 Teams 및 Microsoft 365 Copilot을 선택합니다. 이 채널이 연결되어 있어야 이후 1장의 조직 카탈로그 배포, 3장의 차단 결과를 사용자 화면에서 확인할 수 있습니다.
① 사용할 채널을 확인하고 ② 표시(가용성) 범위를 선택합니다. 이 단계에서 선택한 범위가 관리자 승인 요청 여부를 결정합니다.
Teams + Microsoft 365 채널 게시가 완료된 상태입니다. 게시 완료가 곧 조직 카탈로그 승인·전사 배포 완료를 뜻하지는 않습니다. 조직 전체 노출은 다음 단계의 관리자 승인을 거쳐야 합니다.

8단계 · 관리자 승인 제출

① 채널의 가용성 옵션을 열고 ② 내 조직의 모든 사람에게 표시를 선택합니다. 이 선택이 AI 관리자에게 전달되는 승인 요청을 생성합니다.
제출 전 검토 화면에서 제작자, 설명, 연결된 지식·도구, 요청 권한 요약을 확인합니다. 여기 표시되는 내용이 관리자 검토 화면에 그대로 전달되므로, 설명이 비어 있으면 승인이 지연될 수 있습니다.
조직 공개 여부를 묻는 확인 대화상자에서 예를 선택하면 승인 요청이 제출됩니다.
제출 후에는 승인 대기 상태로 표시됩니다. 새로 고침으로 요청 상태를 확인하며, 이 시점부터는 제작자가 아니라 AI 관리자의 작업(1장)으로 넘어갑니다.

1. 에이전트 승인 및 전사 배포

1단계 · 관리자 승인

요청 상세에서 ① Microsoft Store에 게시 버튼을 선택해 게시 마법사를 시작합니다. 이 화면에서 제작자·업무 목적·지식·도구·요청 권한을 검토하고, 부적절하면 제출을 거부할 수 있습니다.

• 세부 정보 — 제작자·소유자·업무 목적·게시 채널을 확인하고, 제작자·소유자가 식별·검증 가능한가
• 데이터 & 도구 — 연결된 지식 원본과 MCP 도구 목록을 확인하고, 목적·지침 대비 적정한 MCP 도구만 연결되어 있는가(불필요한 광범위 도구 없음), 지식 원본이 민감 사이트·과도한 범위를 포함하지 않는가
• 사용 권한 — 에이전트가 요청하는 API/커넥터 권한이 업무 목적에 비해 과도하지 않은가(최소 권한)
부적절한 경우 승인을 보류하고 제작자에게 수정 요청 후 재제출받습니다.

2단계 · 전사 배포

① 설치 가능 대상과 ② 사전 설치 대상을 지정한 뒤 ③ 다음으로 진행합니다. 설치 가능은 사용자가 원할 때 직접 추가하는 방식이고, 사전 설치는 대상 사용자에게 자동으로 배포되는 방식이므로 영향 범위가 다릅니다.
배포 시 적용될 앱 정책 템플릿을 확인합니다. 조직에 이미 적용 중인 앱 설정 정책이 있는 경우 여기서 함께 확인됩니다.
권한 검토 화면입니다. 이 사례에서는 필요한 권한 없음으로 표시됐지만, 이는 에이전트의 모든 MCP 도구가 무권한으로 실행된다는 뜻이 아닙니다. 도구별 인증·동의는 별도로 적용되며, 실제 데이터 접근은 도구 수준에서 다시 통제됩니다.

Note — Copilot Studio 에이전트는 생성 시점에 API 권한(위임/애플리케이션 권한)을 직접 부여하지 않으며, 실제 권한은 각 도구·커넥터를 사용할 때 런타임에 사용자 동의·연결 단위로 부여됩니다. 따라서 이 화면에 요청 권한이 비어 있는 것은 정상입니다. 반면 Copilot Studio 이외의 플랫폼·방법으로 생성된 에이전트는 요청 권한이 함께 넘어올 수 있으므로, 그런 경우 이 권한 검토 화면에서 요청 권한의 적정성을 확인하면 됩니다.
최종 검토 화면에서 대상·권한·정책을 한 번 더 확인한 뒤 게시합니다.
관리자 처리가 완료된 상태입니다. 배포 직후에는 Teams / Microsoft 365 Copilot 사용자 화면에 반영되기까지 시간이 걸릴 수 있으므로, 사용자 실행 확인은 잠시 후 다시 시도합니다.

4. 에이전트에 대한 기본 접근제어

사용자가 사외(신뢰할 수 없는 네트워크)에서 Copilot Studio 에이전트를 사용하지 못하도록 Entra 조건부 액세스 정책을 만들고, 실제 차단과 로그인 로그의 평가 결과를 확인하는 단계입니다. 접근 제어 대상이 클라우드 리소스가 아니라 에이전트 자체가 됩니다.

전체 순서 한눈에 보기

#항목설정 위치확인 포인트
0역할/권한 준비Entra 관리 센터 > 역할 및 관리자 > 조건부 액세스 관리자정책 생성 전 조건부 액세스 관리자 역할 확인
1사용자 차단 정책 생성조건부 액세스 > 정책 > 새 정책 (사용자 / 대상 리소스 / 네트워크 / 액세스 제어)모든 사용자 → Copilot Studio 에이전트, 사외(비신뢰 네트워크)에서 액세스 차단 → 정책 On
2실제 차단·정책 평가 확인Teams / M365 Copilot에서 에이전트 실행 후 Entra > 모니터링 및 상태 > 로그인 로그사외에서 Copilot Studio 에이전트 실행이 실제로 차단되는지, 로그인 로그의 CA 결과를 확인

1단계 · 사용자 차단 정책 생성

① Entra ID에서 ② 조건부 액세스로 이동해 ③ 새 정책 만들기를 선택합니다. 이 작업에는 조건부 액세스 관리자 역할이 필요합니다.
① 정책 이름을 지정합니다. 이름에 적용 대상·조건(예: 사외 위험 에이전트 사용 차단)을 드러내면 이후 운영·감사에서 구분이 쉽습니다. ② 할당의 사용자 또는 에이전트에서 정책이 적용될 행위자를 지정하는데, 이번 시나리오는 사용자가 에이전트를 사용하는 행위를 통제하므로 ③ 모든 사용자를 선택합니다(운영 시에는 특정 그룹으로 좁히는 것을 권장). 안내에 나오듯 사용자 기반 정책은 사용자가 직접 접근하거나 사용자를 대신해 작동하는 에이전트를 통해 접근할 때 함께 적용됩니다.
① 대상 리소스에서 접근을 통제할 대상을 지정합니다. ② 리소스 선택 > 특정 리소스 선택에서 Microsoft Copilot Studio agent identity blueprint를 지정하면 Copilot Studio로 만든 에이전트가 접근 대상이 됩니다.

Note — 현재 조건부 액세스 리소스 선택기에서 개별 에이전트 ID는 '지원되지 않는 리소스'로 표시되어 단일 에이전트만 개별적으로 지정할 수는 없습니다. 대신 위 블루프린트로 Copilot Studio 에이전트 전체를, 또는 모든 에이전트 리소스로 테넌트의 모든 에이전트를 대상으로 지정합니다.
① 네트워크 조건을 켜고 포함은 모든 네트워크 또는 위치로 둔 뒤, ② 제외 탭에서 모든 신뢰할 수 있는 네트워크 및 위치를 제외합니다. 이렇게 하면 사내(신뢰 네트워크)는 정책에서 빠지고, 사외(비신뢰 네트워크)에서 접근할 때만 정책이 적용됩니다.
여기서 말하는 '신뢰할 수 있는 위치'는 조건부 액세스 > 관리 > 명명된 위치에서 회사 IP 대역 등을 등록하고 신뢰할 수 있음 = 예로 표시해 둔 위치입니다. 본 실습 테넌트에는 회사 IP 대역(예: ME Services·Provisioning/Stockpiling/Teams Workers)이 이미 신뢰 위치로 등록되어 있어, 이 대역 밖(사외)에서 접근할 때 앞의 정책이 적용됩니다.
① 액세스 제어 > 허용을 열고 ② 액세스 차단을 선택합니다. 이 조합으로 '모든 사용자가 사외에서 Copilot Studio 에이전트에 접근하면 차단'이라는 정책이 완성됩니다.
정책 요약을 확인하고 ① 정책 사용을 지정한 뒤 ② 만들기로 생성합니다. 운영 반영 전 영향도를 먼저 보려면 보고 전용(Report-only)으로 만들어 로그로만 평가하고, 실제로 차단하려면 '설정(On)'으로 전환합니다.

주의 — 모든 사용자 + 차단 조합은 광범위 영향을 줄 수 있으므로, 운영에서는 반드시 소규모 그룹으로 먼저 검증한 뒤 확대합니다.

2단계 · 실제 차단·정책 평가 확인

정책을 On으로 둔 상태에서 Teams / M365 Copilot로 대상 Copilot Studio 에이전트를 사외(비신뢰 네트워크)에서 실행하면, 에이전트가 도구 호출을 위해 토큰을 요청하는 시점에 조건부 액세스가 이를 거부해 실제로 차단됩니다. 화면과 같이 오류 코드: IntegratedAuthConditionalAccessBlocked 메시지가 표시되며, 이는 통합 인증이 조건부 액세스 정책에 의해 차단됐음을 명시적으로 나타냅니다.

참고: 조건부 액세스는 새 토큰 요청 시 평가되므로, 정책을 켠 직후 이미 로그인된 세션에서는 토큰 캐시로 인해 즉시 차단되지 않을 수 있습니다. 토큰이 갱신되거나 새 세션·새 도구 연결로 접근할 때 차단이 적용됩니다.
Entra > 모니터링 및 상태 > 로그인 로그에서 사용자 로그인(비대화형) 탭을 열고, 조건부 액세스 열(및 로그인 상세의 조건부 액세스 탭)에서 이 정책의 평가 결과를 확인합니다. 사외에서 대상 에이전트 리소스에 접근한 로그인은 이 정책에 의해 실패(차단)로 기록됩니다.

참고: 비대화형 로그인 로그는 수집·반영까지 다소 지연될 수 있어, 차단 직후에는 로그가 보이지 않을 수 있습니다.

5. 에이전트 리스크 탐지

에이전트의 상호작용에서 발생하는 위험을 서로 다른 계층에서 탐지·수집하는 단계입니다. Purview DLP(민감 정보 유형이 포함된 프롬프트·메시지 차단), Communication Compliance(부적절·비윤리적 상호작용 및 기밀 공유 탐지), 내부 위험 관리(IRM)(에이전트 활동 기반 위험 신호) 세 가지 정책을 만들고, 하나의 에이전트 활동에 대해 DLP·CC·IRM 경고를 함께 확인합니다. 감사 로그 수집이 켜져 있어야 지표·경고가 생성됩니다.

0단계 · 감사 준비

Purview > 감사 > 감사 수집 상태에서 감사 로그 수집이 켜져 있는지 먼저 확인합니다. 감사 로그가 꺼져 있으면 DLP·CC·IRM 정책을 만들어도 분석할 활동 이벤트 자체가 없어 지표·경고가 생성되지 않습니다. 이 단계는 이후 세 정책 모두의 공통 전제입니다.

1단계 · DLP 정책 생성 — Microsoft 365 Copilot

Purview > 데이터 손실 방지 > 정책 > 정책 만들기를 시작하면 “어떤 정보를 보호하시겠습니까?” 화면이 나옵니다. ① 엔터프라이즈 애플리케이션 및 디바이스를 선택합니다. 이 범주에 Microsoft Copilot 환경이 포함되며, Teams / Microsoft 365 Copilot 채널에 게시된 Copilot Studio 에이전트의 상호작용도 이 위치에서 통제됩니다. 이어서 규정에서 사용자 지정 정책으로 시작합니다(Copilot 콘텐츠 보호는 사용자 지정 정책에서만 구성 가능). 이 작업에는 Purview 데이터 보안 AI 관리자 또는 규정 준수 관리자 역할이 필요합니다.
위치 단계에서 ① Microsoft 365 Copilot 및 Copilot Chat 위치만 켭니다. 에이전트가 이 채널을 통해 노출되므로, 이 위치가 에이전트에 전달되는 프롬프트에 적용됩니다.
규칙에서 ① 조건으로 콘텐츠에 중요 정보 유형(SIT) — 이 실습에서는 Credit Card Number를 지정하고, ② 작업으로 Copilot이 콘텐츠를 처리하지 못하도록 제한 > 프롬프트 처리 중을 선택합니다. 즉 민감정보가 포함된 프롬프트의 처리를 차단하고 관리자에게 알립니다.

요약의 HasActivity: UploadText는 '프롬프트 처리 차단' 동작이 내부적으로 표현된 값으로, 별도로 추가한 조건이 아닙니다.
정책 모드에서 ① 정책을 즉시 켭니다를 선택합니다. 시뮬레이션 모드는 실제 차단 없이 영향도만 평가하므로, 실제 차단·경고를 확인하려면 즉시 켜기로 활성화합니다.
정책이 생성되면 DLP 경고에서 정책 일치를 모니터링할 수 있습니다.

⚠️ Notice — M365 Copilot 위치의 프롬프트 처리 차단은 현재 미리 보기로 순차 배포 중이며, 정책 활성화 전파에 시간이 걸립니다. 또한 에이전트 자체 안전장치·모델 콘텐츠 필터가 DLP보다 먼저 응답을 막을 수 있어, DLP 차단 UX와 경고는 지연되어 나타날 수 있습니다. 관련 기능·요건은 Microsoft 365 Copilot용 DLP(공식 문서)를 참고하세요.

2단계 · DLP 정책 생성 — Teams

1단계와 동일하게 Purview > 데이터 손실 방지 > 정책 > 정책 만들기에서 ① 엔터프라이즈 애플리케이션 및 디바이스를 선택하고, 규정에서 사용자 지정 정책으로 시작합니다. 이번에는 Teams 채팅·채널 메시지를 대상으로 하는 별도 정책을 만듭니다.
위치 단계에서 ① Teams 채팅 및 채널 메시지만 켭니다(Exchange·SharePoint·OneDrive·장치 등 나머지 위치는 모두 끔). 에이전트가 Teams 채널에서 상호작용할 때의 메시지 데이터 유출을 통제합니다.
규칙에서 ① 조건으로 콘텐츠에 중요 정보 유형(SIT) — Credit Card Number(메시지 또는 첨부 파일 평가)를 지정하고, ② 작업으로 Microsoft 365 위치의 콘텐츠 제한 또는 암호화를 추가합니다. 이 작업은 보호 대상 SIT가 포함된 Teams 채팅·채널 메시지 전송을 차단(모든 사용자 차단)하고 관리자에게 알립니다.
정책 모드에서 ① 정책을 즉시 켭니다를 선택합니다. 1단계와 동일하게, 실제 차단·경고를 확인하려면 시뮬레이션이 아닌 즉시 켜기로 활성화합니다.
Teams용 DLP 정책 생성이 완료됩니다. Copilot용(1단계)과 Teams용(2단계)을 분리해 두면, 에이전트가 어느 표면(Copilot 채팅 / Teams 메시지)에서 민감정보를 다루는지에 따라 탐지·차단 지점을 명확히 구분할 수 있습니다.

3단계 · 커뮤니케이션 규정 준수 정책 생성

커뮤니케이션 규정 준수 > 정책 > 정책 만들기에서 ① AI 에이전트의 비윤리적 상호작용 탐지 템플릿을 선택합니다. 이 템플릿은 AI 에이전트가 보낸 메시지에서 모욕적·위협적 언어 등 부적절한 텍스트를 탐지합니다(단순 Copilot 채팅이 아니라 에이전트 대상).
① 감독할 AI 에이전트에서 생성된 에이전트 > Microsoft Copilot Studio를 선택하고, ② 검토자를 지정합니다. 커뮤니케이션 규정 준수는 Microsoft 365 Copilot과 Copilot Studio로 만든 에이전트의 프롬프트·응답 상호작용을 분석합니다. 근거: 생성형 AI 상호작용 탐지 정책(공식 문서).
커뮤니케이션 규정 준수 정책 생성이 완료됩니다. 정책 활성화에 최대 1시간, 통신 캡처(경고 생성)에 최대 24시간이 소요됩니다.

4단계 · IRM 에이전트 정책 생성 및 경고 확인

Purview 내부 위험 관리(IRM)에서 에이전트 정책을 만들어 활동 기반 위험 신호를 수집하고 경고를 확인합니다. DLP·CC·IRM은 서로 다른 계층의 신호로, 하나의 에이전트 활동에 대해 세 가지 경고를 교차로 확인할 수 있습니다.

내부 위험 관리 > 정책에서 ①~④ 순으로 에이전트 정책 생성을 시작합니다. 이 작업에는 내부자 위험 관리 분석가 또는 조사자 역할이 필요합니다.
정책 템플릿을 선택합니다. 에이전트 전용 템플릿을 선택하면 에이전트 활동 지표가 기본 세트로 구성됩니다.
① 정책 이름, ② 설명, ③ 다음 순으로 입력합니다. 이름에 적용 범위를 드러내면 이후 경고 분류에 도움이 됩니다.
정책을 적용할 에이전트 범위를 지정합니다. 현재 UI에서는 ① 모든 에이전트가 선택되어 있고 ② 특정 에이전트 선택은 비활성화되어 있습니다. 따라서 정책 이름에 Demo가 들어 있어도 단일 에이전트 범위가 아니라 테넌트 전체 범위로 적용된다는 점에 유의합니다.
우선순위로 다룰 콘텐츠(민감도 레이블·사이트·파일 유형 등)를 선택합니다(①②).

Note — 우선순위 콘텐츠 지정 여부는 위험 점수 산정에 직접 영향을 줍니다. 우선순위로 지정한 콘텐츠(예: 민감도 레이블이 높은 문서, 특정 SharePoint 사이트)에 에이전트가 접근·조작하면 더 높은 위험 가중치가 부여되어 경고 심각도가 올라가고 더 쉽게 트리거됩니다. 지정하지 않으면 모든 콘텐츠가 동일 가중치로 평가되어 중요 자산에 대한 위험 활동이 상대적으로 묻힐 수 있습니다. 따라서 조직의 핵심 자산을 우선순위로 지정해 탐지 민감도를 집중시키는 것이 좋습니다.
앞서 선택한 콘텐츠 각각에 대해 세부 항목을 추가로 지정합니다(①~④). 우선순위 콘텐츠는 위험 점수 가중치에 직접 영향을 줍니다.
알림(경고)을 생성할 범위를 지정합니다(①②).
경고를 유발할 이벤트 트리거를 선택합니다(①②). 에이전트의 어떤 행위를 위험 신호의 시작점으로 볼 것인지 정하는 단계입니다.
트리거 임계값을 지정합니다(①~③). 초기에는 경고가 실제로 생성되는지 확인하기 위해 임계값을 최대한 낮게 잡고, 오탐 추이를 보면서 사내 환경에 맞게 점차 올리는 방식을 권장합니다.
표시기(Indicator) 단계에서 선택한 총 표시기 수(4/4)와 에이전트 지표 분류를 확인합니다. 화면에 선택되어 있다고 해서 해당 이벤트가 실제로 수집·탐지되고 있다는 보장은 아니며, 실제 동작 여부는 경고와 활동 증거로 별도 확인해야 합니다.
탐지 옵션의 위험 점수 부스터에는 에이전트 활동이 그날 평균 활동을 상회하는 경우 등의 조건이 표시됩니다. 앞서 설정한 트리거 임계값·지표 임계값과는 별개이므로 구분해서 검토합니다.
최종 검토 후 정책을 생성합니다.
정책 생성이 완료된 상태입니다. 정책 생성 후 실제 경고가 표시되기까지 최대 24시간이 걸릴 수 있습니다.
경고가 생성된 경우의 확인 경로입니다(①~③). 심각도를 기준으로 에이전트 활동과 관련해 어떤 리스크가 탐지되었는지를 확인합니다.
① 경고를 열어 심각도·위험 점수를 확인하고, ② 우측 경고 세부 정보 패널에서 해당 경고와 연관된 이벤트와 에이전트를 파악합니다.
① 활동 탐색기에서 개별 활동을 선택하면 우측 상세 패널에 활동 세부 정보(작업·워크로드·AI 애플리케이션)와 함께, ② 프롬프트 세부 정보(실제 입력 프롬프트·프롬프트 ID), ③ 응답 세부 사항(응답 ID·중요한 정보 유형)이 표시됩니다. 이를 통해 어떤 프롬프트가 어떤 응답·리소스로 이어졌는지를 활동 종류별로 추적할 수 있습니다. 프롬프트·응답 원문은 내부 위험 관리 조사자 역할을 가진 사용자만 볼 수 있습니다.

6. 에이전트 리스크 기반 접근제어

에이전트가 접근하는 클라우드 앱·커넥터 리소스를 대상으로 조건부 액세스 정책을 적용하고, 위치·네트워크 등 리스크 신호에 따라 허용/차단을 제어한 뒤 로그인 로그로 평가 결과를 검증하는 단계입니다. 앞의 기본 접근제어가 에이전트 자체를 대상으로 했다면, 여기서는 에이전트가 호출하는 리소스(클라우드 앱)를 대상으로 접근을 통제합니다.

1단계 · 대상 정책 생성

Entra 관리 센터 > 보호 > 조건부 액세스 > 정책에서 ① 새 정책을 만들고 ② 이름을 지정합니다. 이 작업에는 조건부 액세스 관리자 역할이 필요합니다.
할당 단계에서 정책 적용 대상을 지정합니다(①~④). 에이전트는 사람 사용자와 달리 Agent ID로 지정하며, 사용자 대상 정책과 섞이지 않도록 대상 범위를 명확히 분리합니다.
① 대상 리소스에서 ② 에이전트가 실제로 호출하는 커넥터·리소스를 지정합니다. 에이전트만 지정하고 실제 접근 리소스를 빠뜨리면 커넥터 호출이 정책 평가에서 누락될 수 있습니다.
조건(네트워크·디바이스·위치 등)을 구성합니다(①~⑤). 에이전트는 사용자 디바이스가 없는 워크로드 형태로 동작하므로, 디바이스 기반 조건을 그대로 적용하면 의도치 않은 차단이 발생할 수 있습니다.

Note — 리스크 신호 출처 구분
이 장에서 에이전트에 적용하는 위험 조건은 Microsoft Entra ID Protection이 산정한 에이전트 위험(Agent risk, 미리 보기)입니다. 이는 5장의 Purview 내부 위험 관리(IRM) 에이전트 경고나 Defender 경고와는 다른 별도의 신호로, IRM·Defender 경고가 그대로 조건부 액세스 조건으로 들어오지 않습니다. 에이전트 위험을 산정하는 위험 기여 활동(탐지 종류)은 공식 문서 에이전트에 대한 ID 보호 — 위험에 기여하는 활동을 참고하세요.
액세스 제어에서 허용/차단과 요구 제어를 지정합니다(①~③).
① 정책 사용 상태를 지정하고 ② 생성합니다. 운영 적용 전에는 보고서 전용(Report-only)으로 먼저 영향도를 확인하는 것을 권장하며, 보고서 전용은 실제로 차단하지 않습니다.

경고를 클릭한 뒤 활동 세부 정보 탭을 열면(위 화면), 해당 탐지의 원천 데이터를 필드 단위로 확인할 수 있습니다. 대표 필드는 다음과 같습니다.

• 에이전트 식별 — AgentName·AgentID·PlatformAgentType(예: AzureAIFoundry)·AgentBlueprintID·ChannelName(예: msteams:COPILOT): 어떤 에이전트가 어떤 플랫폼·채널에서 동작했는지
• 세션·요청 — ConversationId·RequestId·ResponseId·RequestMessages: 실제 요청/응답과 대화 맥락
• 도구 호출 — ToolName(예: mcp_WorkIQWord.GetDocumentContent)·ToolType·ToolID·ToolOutput: 에이전트가 호출한 도구와 그 출력(주입 콘텐츠 포함)
• 위협 분류 — MitreAtlasTactics/Techniques·OWASPCategory·PotentialCauses: 어떤 공격 기법·원인으로 분류됐는지

즉 이 탭 하나에서 어떤 에이전트가, 어떤 채널에서, 어떤 도구를 호출해, 어떤 위협으로 탐지됐는지를 한 번에 파악할 수 있습니다. 우측 세부 정보 패널에서는 심각도·상태·경고 ID·범주 등 경고 메타데이터를 확인합니다.
고급 헌팅에서 탐지 데이터에 에이전트 인벤토리·구성 컨텍스트를 붙이려면 AgentsInfo 테이블을 조인합니다. AgentsInfo는 Microsoft Agent 365의 에이전트 목록·구성·소유자 정보를 담는 테이블로, 탐지 증거 테이블 AlertEvidence에서 EntityType == "AIAgent" 행의 AdditionalFields.AgentId(Entra 에이전트 ID)를 꺼내 AgentsInfo.EntraAgentID와 조인합니다.

주요 컬럼과 조회 가능 정보
• Name — 에이전트 표시 이름
• Owners — 소유자(Entra 개체 ID)
• LifecycleStatus — 운영 상태(Active·Blocked·Uninstalled·Deleted)
• DeclaredTools·McpServers — 선언된 도구·연결된 MCP 서버
• Permissions·PublishedStatus — 요청·부여 권한과 게시 상태
이를 통해 어떤 에이전트가·누구 소유이고·무슨 도구를 쓰며·현재 상태(Active/Blocked)가 무엇인지를 경고 한 건에 활동 단위로 보강할 수 있습니다. 참고: 이 테이블은 기존 AIAgentsInfo를 대체하며(AIAgentsInfo는 2026-07-01 폐기 예정), Agent 365 환경에서는 AgentsInfo를 사용합니다.
KQL — 탐지(경고)에 에이전트 컨텍스트 보강 (EntraAgentID 조인)
AlertEvidence
| where Timestamp > ago(30d)
| where ServiceSource == "Security for AI"
| where EntityType == "AIAgent"
| extend EntraAgentID = tostring(todynamic(AdditionalFields).AgentId)
| join kind=inner (AlertInfo | project AlertId, Title, Severity) on AlertId
| join kind=inner (
    AgentsInfo
    | summarize arg_max(Timestamp, *) by AgentId
    | mv-apply t = DeclaredTools on (summarize Tools = make_set(t.type))
    | project EntraAgentID, AgentName = Name, Owners, LifecycleStatus, Tools
  ) on EntraAgentID
| project AgentName, Owners, LifecycleStatus, Tools, Detection = Title, Severity, EntraAgentID
| order by AgentName asc
KQL — 에이전트 인벤토리·구성 단독 조회 (소유자·도구·MCP·상태)
AgentsInfo
| summarize arg_max(Timestamp, *) by AgentId
| project Name, Platform, EntraAgentID, LifecycleStatus, PublishedStatus,
          Owners, DeclaredTools, McpServers, Permissions
| order by Name asc
CloudAppEvents 테이블(Agent 365 관측 데이터)을 ActionType == "ExecuteToolByGateway"로 필터링해 에이전트의 실제 도구 호출을 조회합니다. 경고(AlertInfo)·증거(AlertEvidence)와 상관 분석하면 하나의 실행 흐름을 재구성할 수 있습니다.

주요 컬럼과 조회 가능 정보
• Timestamp — 도구 호출 시각
• ActionType — 작업 유형(에이전트 도구 호출은 ExecuteToolByGateway)
• Application·AccountDisplayName·AccountObjectId — 어떤 앱·실행 계정이 호출했는지
• IPAddress·CountryCode — 호출 출처 IP·국가
• RawEventData — 도구 호출의 원천 JSON. 여기에 ToolServerName(MCP 서버명)·ServerAddress·AgentName·ToolName·ToolDescription·Operation·ErrorMessage 등 실제 호출된 도구와 파라미터·결과가 담깁니다
이를 통해 어떤 에이전트가 어떤 MCP 도구를, 어디서(IP·국가), 어떤 앱·계정으로 호출했는지를 활동 단위로 추적할 수 있습니다. 참고: 실시간 보호의 감사·차단 동작은 BehaviorInfo에 기록되지만, Copilot Studio 에이전트의 차단 이벤트는 아직 지원되지 않습니다.
KQL — 최근 에이전트 도구 호출 조회
CloudAppEvents
| where Timestamp > ago(7d)
| where ActionType == "ExecuteToolByGateway"
| project Timestamp, Application, AccountDisplayName, IPAddress, CountryCode, RawEventData
| order by Timestamp desc

CloudAppEvents

① 실습 환경을 선택하고 ② 설정을 엽니다. GSA 적용도 환경 단위이므로 같은 환경의 다른 에이전트에도 함께 영향이 갑니다.
① Enable을 On으로 바꾸고 ② 저장합니다. 이 시점부터 해당 환경 에이전트의 아웃바운드 트래픽이 Global Secure Access를 경유합니다.

2단계 · 로그 조회

Entra > 전역 보안 액세스 > 모니터링에서 활성화 상태를 확인합니다(①②).
Gen AI 인사이트 로그에서 에이전트가 실제로 주고받은 트래픽을 조회합니다. Event ID·Transaction ID로 상관 분석하면 하나의 실행에 대한 요청·응답을 이어서 볼 수 있으며, MCP tools/call의 요청 본문과 응답까지 확인할 수 있습니다. 로그 반영에는 지연이 있을 수 있습니다.
